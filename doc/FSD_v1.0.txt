2. System Architecture
2.1 High-Level Architecture
All three client applications communicate exclusively with the single Express API over HTTPS. The API authenticates every request via JWT, enforces RBAC, processes business logic in service modules, and persists data in PostgreSQL. Side effects such as notifications and PDF generation are handled asynchronously via an in-process job queue (Bull + Redis) to keep API response times fast.

2.2 Request Lifecycle
Every inbound HTTP request passes through the following ordered layers before a response is returned:


01Rate Limiter
Reject requests exceeding per-IP or per-user rate limits (express-rate-limit). Returns HTTP 429.
02Body Parser & Helmet
Parse JSON body, set security HTTP headers (helmet.js), sanitize inputs.
03JWT Auth Middleware
Verify Bearer token via Passport.js JWT strategy. Attach decoded user payload (user_id, company_id, role) to req.user. Return 401 if invalid.
04RBAC Permission Guard
Check req.user.permissions against the route's required permission code. Return 403 if insufficient.
05Request Validation
Validate body/params/query against class-validator DTOs. Return 422 with structured errors array on failure.
06Controller
Extract validated inputs, call the appropriate Service method, return shaped response.
07Service
Business logic layer. Orchestrates multiple Repository calls, enforces business rules, triggers async jobs.
08Repository
TypeORM data access layer. All queries are company_id-scoped. No raw SQL except for complex payroll aggregations.
09Audit Log Interceptor
After successful mutation (POST/PATCH/PUT/DELETE), write an audit_log entry asynchronously.
10Global Error Handler
Catch all unhandled errors, classify them, log to Winston + Sentry, return standardized error envelope.

3. Database Schema Overview
3.1 Entity Relationship Summary
The schema is organized into seven functional domains. All tenant-specific tables carry a company_id foreign key that links back to the companies table, providing row-level multi-tenancy isolation.

DomainCore TablesRelationshipsIdentity & Authcompanies, users, roles, permissions, role_permissionsusers → companies, users → roles, roles ↔ permissions (M2M)Organizationdepartments, teams, work_locationsdepartments → companies, teams → departments, work_locations → companiesEmployeesemployees, employee_documents, salary_structuresemployees → users, employees → departments/teams, salary_structures → employeesAttendanceattendance_logs, attendance_requests, overtime_records, shiftsattendance_logs → employees, attendance_requests → attendance_logsLeaveleave_types, leave_balances, leave_requests, holidaysleave_balances → employees + leave_types, leave_requests → employeesPayrollpayroll_cycles, payroll_records, payslipspayroll_records → cycles + employees, payslips → payroll_recordsPlatform / Billingplans, subscriptions, invoices, payments, audit_logssubscriptions → companies + plans, invoices → subscriptions
3.2 Multi-Tenancy Strategy
PeopleOps uses a shared-schema, row-level multi-tenancy model. All tenant data lives in the same PostgreSQL database and tables. Isolation is enforced by:
• Every tenant-scoped table has a company_id UUID column with a NOT NULL constraint and a foreign key to companies.id
• The JWT access token embeds company_id in its payload - the backend always reads company_id from req.user, never from request parameters
• TypeORM repositories are wrapped in a CompanyRepository base class that automatically appends WHERE company_id = :cid to every query
• Super Admin users have no company_id in their token and use a separate SuperAdminGuard - they cannot access tenant data except through the controlled impersonation flow

Why shared schema?
For a 100-1,000 employee target market, shared schema gives the best balance of operational simplicity (single set of migrations, single backup, single connection pool) and resource efficiency. Dedicated schemas or databases per tenant are reserved for Enterprise tier in Phase 2.

5. Security & Auth Flow
5.1 Authentication Strategy
Authentication is implemented using Passport.js with two strategies: a Local Strategy for username/password login and a JWT Strategy for all subsequent authenticated requests. Passwords are hashed with bcrypt (cost factor 12). All auth endpoints are rate-limited to prevent brute-force attacks.

5.2 JWT Token Flow


01User Submits Credentials
POST /auth/login with { email, password }. Local Strategy validates credentials against bcrypt hash.
02Tokens Issued
On success, server generates two tokens: Access Token (JWT, 15 min expiry, signed with ACCESS_TOKEN_SECRET) and Refresh Token (opaque UUID, 7 days, stored in refresh_tokens table).
03Token Storage
Access Token returned in response body. Refresh Token set as HttpOnly, Secure, SameSite=Strict cookie - not accessible to JavaScript.
04Authenticated Request
Client sends Access Token as Authorization: Bearer <token>. JWT Strategy verifies signature and expiry, attaches { user_id, company_id, role, permissions } to req.user.
05Token Refresh
When Access Token expires (401), client calls POST /auth/refresh. Server validates Refresh Token from cookie, issues new Access Token. Refresh Token is rotated (old one invalidated).
06Logout
POST /auth/logout deletes the Refresh Token record from DB and clears the cookie. All subsequent refresh attempts fail.
07Password Reset
POST /auth/forgot-password issues a time-limited (1 hour) signed reset token sent via email. POST /auth/reset-password validates token and updates password hash.
5.3 Role-Based Access Control (RBAC)
After JWT verification, the RBAC middleware resolves the user's permissions array from the role_permissions join table (cached in Redis with a 5-minute TTL per user). Route handlers declare their required permission using a decorator. The guard checks whether the resolved permissions array includes the required code.

// Route declaration example (Express + TypeScript)
router.post(
  '/payroll-cycles/:id/run',
  requirePermission('payroll:run'),   // Guard checks req.user.permissions
  payrollController.runCycle
);

// JWT Payload shape
interface JwtPayload {
  user_id:    string;   // UUID
  company_id: string;   // UUID - always present for tenant users
  role:       string;   // Role name e.g. 'HR Admin'
  permissions: string[]; // ['payroll:run', 'attendance:approve', ...]
  iat: number;
  exp: number;
}
5.4 Super Admin Isolation
• Super Admin tokens contain no company_id and use a separate SuperAdminJwtStrategy with a different secret (SUPER_ADMIN_TOKEN_SECRET)
• Super Admin routes are mounted under /super-admin and protected by a dedicated SuperAdminGuard that rejects any token containing a company_id
• User impersonation (accessing a tenant's dashboard for support) generates a short-lived (30 min), non-renewable scoped token containing the target company_id - every action taken with it is tagged impersonated: true in audit_logs
• Super Admin login requires TOTP-based MFA (authenticator app) in addition to password



6. Approval Workflow Engine
6.1 Dynamic Multi-Level Approval
Each company can configure a custom approval chain per module (leave, attendance corrections, etc.) via the workflows and approval_steps tables. A workflow has ordered steps, each mapped to a role. When an approvable entity is created, the engine determines the current pending step and routes the notification to all users holding that role within the company.

TablePurposeworkflowsDefines that a company has a workflow for a given module (e.g. leave). Can be activated or deactivated.approval_stepsEach row is one step in a workflow. step_order (1, 2, 3...) determines sequence. role_id identifies who must act at that step.approval_logsImmutable append-only record of every approve/reject action with timestamp and actor.
6.2 Approval Flow Execution

01Entity Created
Employee submits leave request. Status set to pending. WorkflowService.initiate(entity_type, entity_id) called.
02Resolve Current Step
Engine queries approval_steps WHERE workflow_id = ? ORDER BY step_order ASC and finds the first step with no corresponding approval_log entry.
03Notify Approvers
All users in the company holding the required role_id for that step are notified via email, push, and SMS.
04Approver Acts
Approver calls PATCH /leave-requests/:id/approve or /reject. RBAC guard verifies they hold the correct role for the current step.
05Log & Advance
Approval action is written to approval_logs. Engine checks if more steps remain.
06Final Approval
If no more steps remain, entity status is set to approved. Leave balance is deducted. Employee notified.
07Rejection at Any Step
If any approver rejects, entity status is immediately set to rejected. No further steps are processed. Employee notified with reason.


7. Payroll Computation Flow
7.1 Trigger Modes
ModeHow It WorksManualHR Admin clicks Run Payroll in the Admin Dashboard. Calls POST /payroll-cycles/:id/run. Immediate synchronous response with job queued.Auto-TriggeredA Bull cron job fires on the configured date (e.g. 25th of each month). Creates a payroll_cycle record and enqueues the computation job automatically. HR Admin still must review and finalize.Re-RunPayroll can be re-run any number of times before the cycle is finalized. Re-running overwrites all payroll_records for that cycle. Once finalized, the cycle is locked - no further changes allowed.
7.2 Computation Steps
The PayrollWorker (Bull job processor) executes the following steps for each active employee in the company:


01Fetch Employees
Query all employees WHERE company_id = ? AND employment_status IN (active, probation, notice). Exclude terminated employees.
02Resolve Salary Structure
For each employee, fetch the salary_structures record with the latest effective_from date that is <= the first day of the payroll month.
03Calculate Working Days
Derive total working days in the cycle month by subtracting weekends and any holidays from the holidays table for that company.
04Calculate Present Days
Count attendance_logs WHERE employee_id = ? AND attendance_date BETWEEN cycle_start AND cycle_end AND status IN (present, half-day).
05Attendance Deduction
If present_days < working_days: deduction = (absent_days / working_days) * basic_salary. Half-days count as 0.5.
06Leave Deduction
Fetch approved leave_requests in the cycle period. For each unpaid leave day (balance already exhausted), add to deductions.
07Overtime Addition
Sum approved overtime_records.hours for the employee in the cycle period. overtime_pay = hours * (basic_salary / (working_days * 8)).
08Compute Net Salary
net_salary = gross_salary - attendance_deduction - leave_deduction - other_deductions + overtime_pay.
09Persist Record
Upsert payroll_records (payroll_cycle_id, employee_id) with computed values. Mark cycle status = computed.
10Queue Payslip Jobs
For each record, enqueue a PdfWorker job to generate the payslip PDF, upload to S3/Spaces, and store the URL in payslips table.

8.3 Delivery Architecture
Notifications are never sent synchronously in the HTTP request cycle. All notification dispatch is handled by Bull job workers to ensure API response times are unaffected by third-party provider latency or failures.

// Notification dispatch flow
1. API handler completes business logic (e.g. leave approved)
2. NotificationService.dispatch(event, payload) is called
3. NotificationService enqueues a job to the 'notifications' Bull queue
4. Response is returned to the client immediately (no blocking)
5. NotificationWorker picks up the job asynchronously
6. Worker resolves recipients, renders templates, calls provider APIs
7. Delivery result (success/failure) is logged
8. Failed jobs are retried up to 3 times with exponential backoff
9. Permanently failed jobs move to the dead-letter queue for inspection

9.2 Global Error Handler
A single Express error-handling middleware (4-argument middleware) is registered last in the middleware chain. All thrown errors - whether explicitly thrown AppError subclasses or unexpected runtime errors - are caught here, classified, formatted, and returned as the standard error envelope.

// src/common/errors/error-handler.ts
export function globalErrorHandler(
  err: Error,
  req: Request,
  res: Response,
  next: NextFunction
): void {
  const isAppError = err instanceof AppError;

  const statusCode = isAppError ? err.statusCode : 500;
  const code       = isAppError ? err.code : 'INTERNAL_ERROR';
  const message    = isAppError ? err.message : 'An unexpected error occurred';

  // Log to Winston always
  logger.error({ code, message, stack: err.stack, path: req.path });

  // Send to Sentry for 5xx errors
  if (statusCode >= 500) Sentry.captureException(err);

  res.status(statusCode).json({
    success: false,
    error: { code, message, ...(err instanceof ValidationError && { errors: err.errors }) }
  });
}

10. Deployment & Infrastructure
10.1 Target Platform
The initial deployment targets DigitalOcean, Railway, or Render - all of which offer managed PostgreSQL, Redis, and container hosting with minimal DevOps overhead. The architecture is designed to be cloud-agnostic: all configuration is environment-variable-driven and all services are containerized with Docker, so migration to AWS, GCP, or Azure in Phase 2 requires no application code changes.
