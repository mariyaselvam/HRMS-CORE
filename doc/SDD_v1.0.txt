1.  Database Design
PostgreSQL · TypeORM · Row-Level Multi-Tenancy
1.1 Entity Relationship Overview

1.2 Multi-Tenancy Strategy
PeopleOps uses a shared-schema, row-level multi-tenancy model. All company data lives in the same PostgreSQL database. Isolation is enforced at three levels:

LevelMechanismWhere EnforcedDatabasecompany_id NOT NULL FK on every tenant tablePostgreSQL constraintsORMBaseRepository automatically appends WHERE company_id = :cid to all queriesTypeORM custom repository base classAPIcompany_id extracted from JWT payload - never accepted from request params or bodyJWT middleware + TypeScript typesSuper AdminSuper Admin tokens carry no company_id and are validated by a separate strategySuperAdminGuard middleware

2.4 Versioning & Deprecation Strategy
• All endpoints are prefixed with /v1. Breaking changes require a new version prefix /v2.
• Deprecated endpoints return a Deprecation: true response header with a Sunset date.
• Old versions are supported for a minimum of 6 months after a new version is released.
• Non-breaking additions (new optional fields, new endpoints) do not require a version bump.



3.  Auth & Security Design
Passport.js · JWT · RBAC · bcrypt · Helmet
3.1 Authentication Strategy
StrategyLibraryPurposeLocal Strategypassport-localValidates email + bcrypt password on POST /auth/loginJWT Strategypassport-jwtValidates Bearer token on all protected routesSuper Admin JWTpassport-jwt (separate instance)Uses different secret, rejects tokens with company_id
3.2 Token Lifecycle Flow

01Login
POST /auth/login. LocalStrategy verifies email + bcrypt hash (cost factor 12). On success → generate tokens.
02Issue Tokens
Access Token: JWT signed with ACCESS_TOKEN_SECRET, 15min expiry, payload: { user_id, company_id, role, permissions[] }. Refresh Token: UUID stored in refresh_tokens table with expiry 7 days.
03Store Tokens
Access Token returned in response body. Refresh Token set as HttpOnly Secure SameSite=Strict cookie.
04Authenticated Request
Client sends Authorization: Bearer <token>. JwtStrategy verifies signature + expiry, attaches decoded payload to req.user.
05Token Expiry
Access Token expires (401). Client calls POST /auth/refresh with cookie. Server validates refresh token from DB, issues new access token, rotates refresh token.
06Logout
POST /auth/logout. Deletes refresh token from DB. Clears cookie. All future refresh attempts fail.
07Password Reset
POST /auth/forgot-password issues a signed 1-hour reset token sent by email. POST /auth/reset-password validates token + updates bcrypt hash.
3.3 Role-Based Access Control (RBAC)
After JWT verification, the RBAC middleware resolves the user's permissions from the role_permissions table. Results are cached in Redis with a 5-minute TTL per user_id. Route handlers declare required permissions via a decorator.

// Permission guard usage

  requirePermission('payroll:run'),
  payrollController.runCycle
);

// JWT payload interface
interface JwtPayload {
  user_id:     string;
  company_id:  string;    // absent for Super Admin tokens
  role:        string;
  permissions: string[];  // ['payroll:run','attendance:approve',...]
  iat: number; exp: number;
}
3.4 Super Admin Isolation
• Super Admin JWT uses a separate SUPER_ADMIN_TOKEN_SECRET - tokens are cryptographically incompatible with tenant tokens
• SuperAdminGuard rejects any token that contains a company_id field
• All /super-admin routes mounted separately and protected exclusively by SuperAdminGuard

5.  Approval Workflow Engine
Dynamic multi-level · configurable per company · full audit trail
5.1 Design Overview
The workflow engine is a generic, reusable service that handles multi-level approvals for any approvable entity (leave requests, attendance corrections, overtime). Each company configures its own approval chain per module via the workflows and approval_steps tables. The engine is completely decoupled from the entity it is approving.

// WorkflowEngine interface
interface WorkflowEngine {
  initiate(entityType: string, entityId: string): Promise<void>;
  approve(entityType: string, entityId: string, actorUserId: string, comment?: string): Promise<void>;
  reject(entityType: string, entityId: string, actorUserId: string, reason: string): Promise<void>;
  getCurrentStep(entityType: string, entityId: string): Promise<ApprovalStep | null>;
}
5.2 Execution Flow

01Initiate
WorkflowEngine.initiate() is called after the entity is created. Looks up the active workflow for the module. If no workflow configured, entity is auto-approved.
02Resolve Step
Query approval_steps for the workflow ordered by step_order. Find the first step with no corresponding approval_logs entry for this entity_id.
03Notify Approvers
Query users WHERE role_id = step.role_id AND company_id = entity.company_id. Enqueue notification job for each approver (email + push + SMS).
04Approval Action
Approver calls PATCH /:entity/:id/approve. RBAC guard checks approver holds the correct role for the current step. Guard also checks it's actually their turn.
05Log Action
Write approval_logs entry: { entity_type, entity_id, action: 'approve', acted_by, acted_at, comment }.
06Check Remaining Steps
Query approval_steps again. Are there more steps without a log entry? If yes - notify next step approvers.
07Final Approval
All steps approved. Update entity status = approved. Trigger post-approval side effects (balance deduction, notification to employee).
08Rejection
Any approver rejects at any step. Entity status = rejected immediately. No further steps processed. Employee notified with rejection_reason.
5.3 Escalation & Timeout Rules
RuleBehaviourConfigurationReminder notificationIf an approver has not acted within 24 hours, a reminder notification is sentHardcoded at 24h in MVP; configurable per workflow in Phase 2EscalationIf an approver has not acted within 48 hours, the request is escalated to the next role in the chainPhase 2 feature - flagged in workflows tableAuto-approvalIf no workflow is configured for a module, entities are immediately set to approvedDefault behaviour - HR Admin must explicitly configure a workflow to require approvalWithdrawalEmployee can withdraw a pending entity at any step before the current step is acted onstatus = withdrawn. All in-progress approval steps are cancelled.

7.1 Storage Strategy
File storage uses an S3-compatible object storage service (DigitalOcean Spaces or AWS S3 - configured via environment variables). The application is fully storage-agnostic: the StorageService uses the AWS SDK (which works with any S3-compatible provider).

Security
No file is ever publicly accessible. All access is via time-limited pre-signed URLs generated on demand by the API. The frontend never stores or caches the signed URL - it requests a fresh one each time.
7.2 Payslip PDF Generation
Payslip PDF generation is handled by a dedicated BullMQ worker (PdfWorker) triggered after payroll finalization. This is never done synchronously in the HTTP request.


01Trigger
POST /payroll-cycles/:id/finalize sets cycle status = finalized and enqueues one PdfWorker job per payroll_record in the cycle.
02Load Data
PdfWorker fetches full payroll_record with employee details, company details, and salary breakdown from PostgreSQL.
03Render Template
Render a pre-defined HTML payslip template (Handlebars or EJS) with the payroll data injected. Template includes company logo, employee info, and line-item breakdown.
04Generate PDF
Pass the rendered HTML to Puppeteer (headless Chromium) or pdfmake to produce a PDF buffer. pdfmake is lighter - preferred for containerized environments.
05Upload to Storage
Upload the PDF buffer to S3/Spaces at the path: payslips/{company_id}/{year}/{month}/{employee_code}.pdf
06Store Record
Insert a row into payslips table with payroll_record_id, pdf_url (S3 key), file_size_bytes, generated_at.
07Notify Employee
Enqueue a notification job: PAYSLIP_READY event for the employee. Email + push + optional SMS.
7.3 Employee Document Uploads

9.2 Global Error Handler
// src/common/errors/error-handler.ts
export function globalErrorHandler(
  err: Error, req: Request, res: Response, _next: NextFunction
): void {
  const isKnown  = err instanceof AppError;
  const status   = isKnown ? err.statusCode : 500;
  const code     = isKnown ? err.code       : 'INTERNAL_ERROR';
  const message  = isKnown ? err.message    : 'An unexpected error occurred';

  logger.error({ code, message, path: req.path, stack: err.stack });

  if (status >= 500) Sentry.captureException(err);

  res.status(status).json({
    success: false,
    error: {
      code,
      message,
      ...(err instanceof ValidationError && { errors: err.errors }),
    }
  });
}

11.4 Database Performance
• All queries are company_id-scoped - partial indexes on company_id dramatically reduce scan size as tenant count grows
• attendance_logs is the highest-volume table - composite index on (employee_id, attendance_date) covers the vast majority of queries
• PgBouncer runs in transaction pooling mode - keeps connection count low even under high concurrency
• TypeORM lazy loading is disabled - all relations must be explicitly joined using QueryBuilder to prevent N+1 queries
• Long-running payroll aggregation queries use a read replica in Phase 2 to avoid blocking the primary
• audit_logs is append-only and high-volume - consider partitioning by created_at month in Phase 2



12.  CI/CD Pipeline Design
GitHub Actions · Docker · Automated Tests · Zero-Downtime Deploy
12.1 Pipeline Stages (Full Detail)
Trigger: push to feature/* or PR to main

Stage 1: LINT & TYPE CHECK
  - npx eslint src/ --max-warnings 0
  - npx tsc --noEmit
  ✗ Block merge on failure

Stage 2: UNIT TESTS
  - jest --testPathPattern=src --coverage
  - Coverage gates: statements >= 80%, branches >= 75%
  ✗ Block merge on failure

Stage 3: INTEGRATION TESTS
  - docker-compose up -d postgres redis (ephemeral test containers)
  - Run TypeORM migrations on test DB
  - jest --testPathPattern=test/integration
  - docker-compose down
  ✗ Block merge on failure

Stage 4: SECURITY AUDIT
  - npm audit --audit-level=high
  ✗ Block on high/critical CVEs

Trigger: merge to main

Stage 5: BUILD & PUSH
  - docker build -t registry/api:${COMMIT_SHA} .
  - docker push registry/api:${COMMIT_SHA}

Stage 6: MIGRATE
  - Run pending TypeORM migrations against production DB
  ✗ Halt deploy if migration fails

Stage 7: DEPLOY
  - Rolling deploy: new container starts, health check passes, old terminates
  - Angular apps: npm run build:prod → upload to CDN → invalidate cache

Stage 8: SMOKE TEST
  - GET https://api.peopleops.com/health → expect 200
  ✗ Auto-rollback to previous image if non-200
